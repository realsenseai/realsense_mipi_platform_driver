Layer 1 — kernel UAPI

Two codes that belong to this camera alone

The VI format table is SoC-wide: every row in it is a candidate for every sensor on the chip. A row keyed on the standard MEDIA_BUS_FMT_JPEG_1X8 would be offered to any JPEG sensor on the board, carrier geometry and all. These two private codes keep the carrier rows reachable only from the D58x colour node.

Layer 2 — nvidia-oot VI capture

A line length that does not follow the picture

Every geometry knob the extended row already had — frame_x_scale, frame_y_scale, frame_x_align — scales the picture. A compressed frame has no picture geometry to scale from: the camera emits fixed 1280-byte lines and stops when the bitstream ends. So the new field substitutes the line length outright, and the variable-height flag from the previous change handles the early stop.

Buffer size by substitution, and a clear at every queue

tegra_channel_update_format() and __tegra_channel_try_format() are the pair that must agree, or TRY_FMT and S_FMT report different buffer sizes; both now replace the computed size with the carrier budget and report bytesperline = 0, because a carrier line is not a picture line pitch. The clear is the other half of the change: the capture hardware writes only the lines that arrive and never touches the rest, so without it the tail of a short H.264 frame was the tail of an earlier frame, and the decoder followed it. A buffer that cannot be cleared is refused at QBUF rather than captured into.

Memory models

All three vb2 models are covered, and each needs its own treatment: USERPTR clears through clear_user() in the QBUF caller's own process context, MMAP is coherent and only needs the barrier, and DMABUF is bracketed by dma_buf_begin/end_cpu_access(). Clearing runs from buffer_prepare, which vb2 calls after mapping and before its own cache sync.

How this page was produced

These patches sit late in their series, so their context depends on every patch before them; a patch file read on its own does not show what the driver ends up looking like. Both the nvidia-oot and kernel-jammy-src trees were seeded from their pristine NVIDIA state at tag jetson_36.4.3, and the full JetPack 6.2 series was replayed in order with git apply — the ten patches in nvidia-oot/6.2/ and the seven in kernel/kernel-jammy-src/6.2/ — once from the base branch and once from the PR head. kernel/realsense/d4xx.c is not patched; it is linked into the tree as it stands in the repository, so its copy was taken from each side directly. All four applications were clean, with no fuzz, and the diffs above are between the two results.

  • Base is the merge-base with dev (0321f55); head is RSDEV-13306-clear-buffer at 1c95b9e.
  • Line numbers in the gutter are the PR-head line numbers, so they match the file after the change.
  • Context is six lines for the headers and eight for the C files; ⋯ marks a skipped stretch.
  • The JetPack 7.x stack receives the same changed lines through its own 0008 and 0013/0015 carriers; only the surrounding upstream context differs (noble vs jammy, and a different vi5_setup_surface).
